# Changelog

What changed in Kooks and how each change was verified, newest first. Kooks has no tagged releases yet; `package.json` has said 0.2.0 since the first publication. Add an entry under **Unreleased** with every change: what changed, the checks run with their counts, and what was not exercised.

## Unreleased

### iPhone releases through TestFlight

The **Phone release** workflow now also puts the iPhone app on TestFlight, beside the Android release, so an iPhone gets every release from the TestFlight app. A new job on a macOS runner archives the app, signs it for the App Store, checks its version, build number and Apple Distribution signature, and uploads it with `altool`. It signs without a Mac or a person in the loop: `scripts/ios-signing.mjs` uses an App Store Connect API key to find the bundle ID (registering it if needed) and the app's record, the Apple Distribution certificate made from a key kept in the secrets (creating it from a signing request the first time and after it expires, so the key never goes to Apple and certificates don't pile up), and an App Store provisioning profile named after that certificate, then switches only the App target to manual signing for that run, since a Swift package's resource bundle refuses a profile. The keys sit in a temporary keychain that the job deletes. Until the four secrets exist, the iPhone half warns and does nothing; a missing app record stops it before the build with what to create. **Run workflow** now asks for which phones (both, Android or iPhone), so one half can be run again alone. Pull requests that touch either release build run an unsigned device archive of the iPhone app.

`scripts/ios-release-key.sh` stores those secrets from the owner's computer: given the downloaded API key and its Issuer ID, it makes the certificate key with `openssl` (or keeps the one already made), keeps everything in a folder only they can read with a README, and stores the four secrets through the GitHub CLI or says what to paste. Two things App Store Connect checks on upload are fixed: the app icon had an alpha channel (now flattened, pixel for pixel the same; `scripts/native-assets.mjs` makes it that way), and `Info.plist` now declares `ITSAppUsesNonExemptEncryption` false, as Kooks uses only the HTTPS built into iOS. `docs/native-app.md` (iPhone, Making a release, the device check) and `docs/handoff.md` follow.

`npm run format:check`, `npm run lint` and `npm test` (187 tests: 186 passed, the OCR case skipped; 12 new, which run the signing script against a stand-in App Store Connect for a first release, a later one, a missing app record, a full certificate allowance and refused credentials, and check its token, key handling, profile reading, export options and project change, the icon and the encryption answer) and `npx playwright test` (58: 57 passed; the spent sign-in link test times out in this container as on `main`) pass, and `actionlint` and `shellcheck` find nothing new. The key script was run here with a made-up API key, including a second run that kept the certificate key and refusals of a wrong Issuer ID and a file that isn't a key. Not exercised: anything against Apple. There is no developer account yet, so the API calls ran only against a stand-in in the tests, and the signed archive, export and upload wait for the first real release; this pull request's own run checks the unsigned device archive.

### The iPhone goes back with a swipe from the edge

An iPhone has no back button, and most of the app’s pages have no Back of their own, so on an iPhone the tabs were the only way back from a recipe or a meal. The app's web view now takes Safari's swipe from the left edge (`allowsBackForwardNavigationGestures`, on a `KooksViewController` in `ios/App/App/SceneDelegate.swift`). It goes back through the same history as Android's back button, so an editor with unsaved changes asks first, and it stops at the first page the app opened. `docs/native-app.md` and its device check say so.

`npm run format:check`, `npm run lint` and `npm test` (175 tests: 174 passed, the OCR case skipped; 1 new, which checks the scene delegate) pass, and the Native builds workflow compiles the iOS app. Not exercised: the gesture on an iPhone or in a simulator.

### Signed Android releases, version numbers from package.json, and phones that follow dark mode

A new **Phone release** workflow (`.github/workflows/phone-release.yml`) turns `main` into an Android release when run from the Actions tab. It builds the app, signs the APK with the household's release key from two Actions secrets, checks the signature with `apksigner`, checks the package name, version and build number with `aapt2` and that the APK is not debuggable, and publishes a GitHub pre-release `v<version>` with `kooks-<version>.apk`, its SHA-256 and the signing certificate's fingerprint. It runs only on `main` and refuses a version already released. Pull requests that touch the Android build run the same build with a throwaway key and publish nothing, so the release key never reaches them. `android/app/build.gradle` signs a release only when it is given the key (`KOOKS_ANDROID_KEYSTORE`, a PKCS #12 file). `scripts/android-release-key.sh` makes that key once on the owner's computer with `openssl`: a 4096-bit RSA key valid for 30 years, in a folder only they can read, with its password, its certificate and a README. It stores the two secrets through the GitHub CLI or says what to paste, and it refuses to replace a key that already exists.

Both phone apps now take their version from `package.json`: `npm run native:version` (`scripts/native-version.mjs`, run by `npm version`) writes Android's `versionName` and `versionCode` and iOS's `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, with the build number major × 10000 + minor × 100 + patch (0.2.0 is now build 200 on both, was 1). `npm test` fails if the native projects say anything else.

Both native projects pinned the light look, so the app never followed a phone in dark mode, although in a browser it does: iOS set `UIUserInterfaceStyle` to Light in `Info.plist`, and Android's `Theme.AppCompat.Light` themes make the web view report `prefers-color-scheme: light` whatever the phone says. Both now follow the phone (DayNight themes on Android, with a dark launch background), and the status and navigation bars follow the look chosen in **Household › Look and units**, so their text stays readable on a look that differs from the phone's.

`docs/native-app.md` gains **Releases**: version numbers, the release key and how to keep it, the steps of a release, installing on Android (including Google's coming developer-verification rules for sideloaded apps), the two ways onto an iPhone, and a device check of about 20 minutes per phone. `docs/handoff.md` follows.

`npm run format:check`, `npm run lint`, `npm test` (130 tests: 129 passed, the OCR case skipped; 4 new for version numbers, build numbers, the light look and the bars) and `npx playwright test` (52: 51 passed; "a used or unknown sign-in link explains itself" times out waiting for the quiet passkey suggestion in this container on unchanged `main` too) pass. The key script was run here: Java's `keytool` and `jarsigner` read and sign with its key, including one exported with the older encryption macOS's LibreSSL uses. Not exercised here: Gradle, `apksigner` and `aapt2` (no Android SDK in the cloud container; this pull request's own Phone release run builds the signed APK), a release with the real key, which waits for the owner to make it, any phone, and the dark mode in a native web view.

### Deleting an old address's account from the terminal

`node scripts/accounts.mjs remove <address>` deletes an account with its passkeys, signed-in devices, waiting sign-in links and invitations (to it and from it), takes it out of every household, and clears it as the maker of any household, so the address is left nowhere in the sign-in tables. Taking someone out under Household › Members leaves them an account that can still sign in and start a household of its own, with its own assistant allowance on the host's key, which matters when someone else may now hold an old mailbox: the case in the runbook's owner steps, which now end with `remove` in place of Members. It refuses a household's last owner and the `KOOKS_OWNER_EMAIL` address, which the server would give a new account at its next start. A household the address alone is in, such as one someone else started with it, stops it too, unless `--leave-empty` says to leave that household with nobody in it; `owner <address> --household <id>` gives it an owner again. Run without `KOOKS_OWNER_EMAIL` in its environment, as in a one-off container, it warns that it can't tell which address is the server's owner, and the runbook passes the address to such a container. The runbook also says what to do when the old address brought others into a household (remove them first, then the old address with `--leave-empty`), and that with `KOOKS_OPEN_SIGNUP` on a deleted address can make a new account. `web/auth.js` gains `deleteAccount`, which no route reaches. The hosting guide and SECURITY.md say what removal leaves and how to delete an account. This follows the security review of the recovery runbook.

### Off-site copies to an S3-compatible bucket

With `KOOKS_BACKUP_S3_URL`, `KOOKS_BACKUP_S3_ACCESS_KEY_ID` and `KOOKS_BACKUP_S3_SECRET_ACCESS_KEY` set, each automatic copy also goes to a bucket on Amazon S3, Cloudflare R2, Backblaze B2, MinIO or anything else that speaks the protocol (`web/offsite.js`), so losing the server no longer loses the kitchen. Requests are signed with AWS Signature Version 4 by hand, without an SDK; each file carries its SHA-256 for the storage to check, and the manifest goes last, so a copy in the bucket with a manifest is whole. The server only writes there, never listing, reading or deleting, so its key can be write-only and the bucket's lifecycle rule does the pruning. When the bucket can't be reached the copy stays on the server, the owner's Backup page and the log say why, the monitor gets `/fail`, and Kooks sends the newest copy again an hour later; `/healthz/backups` answers 503 once no copy has reached the bucket for a day and a half. The server refuses to start with only some of the three settings. `node scripts/backup.mjs` gains `send`, `remote` (each copy in the bucket with its time, records and accounts, so the empty kitchen's copies after a loss are not taken for the one to bring back) and `fetch`, and a `snapshot` goes off-site too. The runbook's lost-volume steps now start with fetching from the bucket.

The signatures match botocore's for four requests (path- and host-style buckets, a space in the prefix, a listing query, a port), and the test bucket checks each request's signature as it arrives. On the Docker image with a stand-in bucket on the host, a copy taken in the terminal was sent and listed; the volume was then deleted, and in the new, empty kitchen the copy was listed, fetched, checked and staged, after which the restart brought back the recipes and the owner's signed-in session. A minute later the empty kitchen's own first copy went to the bucket too, and `remote` told the two apart by their records. `npm run format:check`, `npm run lint`, `npm test` (168 tests: 167 passed, the OCR case skipped; 6 new for signing, settings, sending and fetching, a manifest naming other files, the schedule's failures and retries, and the owner's view) and `npx playwright test` (58 tests; 57 passed here and the spent sign-in link test timed out as on `main`) pass. Not exercised: a real provider, a real lifecycle rule, and copies of hundreds of megabytes.

### Automatic backups of the whole server

The server now copies every household's cookbook, and the accounts with their members, passkeys and sessions, once a day while it runs (`web/backups.js`), unless `KOOKS_BACKUPS=off`. Each copy is a folder in `backups/` beside the database (`/data/backups` in the image) holding each database as SQLite's `VACUUM INTO` writes it, one consistent moment taken in a worker thread while people keep cooking, checked with SQLite's integrity check, compressed, and listed with its checksum and record count in a manifest. Only a complete, checked copy lets older ones go: Kooks keeps the newest copy of each of the last 7 days and 4 weeks that have one, so a damaged database or a long outage never costs the copies already kept. A copy is skipped, and reported, when it would leave less than 1 GB free on the disk. `KOOKS_BACKUP_DIR`, `KOOKS_BACKUP_EVERY_HOURS`, `KOOKS_BACKUP_KEEP_DAILY` and `KOOKS_BACKUP_KEEP_WEEKLY` change the folder, interval and retention.

Whoever runs the server sees on Household › Backup when the last copy was taken and how many are kept, and a plain warning when the last attempt failed or none has been taken for a day and a half; other members only learn that copies exist. `GET /healthz/backups` answers 503 for an uptime monitor once copies are late, and `KOOKS_BACKUP_PING_URL` pings a monitor such as healthchecks.io after each attempt (with `/fail` after a failed one), which also raises the alarm when the server is down. `node scripts/backup.mjs` gains `snapshot`, `list`, `check`, `stage` and `unstage`. A restore is staged from the container's terminal while the server runs and goes in place at the next start, before any database opens; the files it replaces move to `replaced-<time>/` beside the database, and an interrupted restore finishes at the following start. The Docker image now includes `scripts/backup.mjs`, which the hosting guide already told operators to run on the server but the image left out.

### Who made each change, and which person at the table a member is

Every change now records who made it, in a new `actor` column of the cookbook's history: a member by an opaque account id (never their address) with the person at the table they were linked to then, an agent for changes made through MCP, or the kitchen's own computer with sign-in off (the browser on a loopback server, and `scripts/backup.mjs restore`). The column is added in place on first open without a new schema version, so an older server still opens the file and leaves its own actions unnamed. `history_list` names who made each action, by the name of the member's person at the table and never by address, says which actions were the reader's own (`you`), and gives each changed record its current title and whether it was left archived.

A member says which person at the table they are with `POST /api/auth/household/person` (one already at this household's table, or `null` for none); each person stands for one member at most. The link is kept with the membership in the sign-in tables, not in the cookbook, so a cookbook and its portable backups hold no sign-in addresses or links, and a member who leaves or is removed takes only the link: their person stays at the table, and history still names their changes by it. ### The server signs the phone app in with an emailed code

The phone app is about to run the redesigned app against the household server, where an emailed link cannot reach it and a passkey cannot serve each household's own address. The server now signs it in with a code instead: `POST /api/auth/code` emails a member a six-digit code (and answers every address the same way, at once, as links do), and `POST /api/auth/code/confirm` takes the address and the code and returns a device token, which the app sends as `Authorization: Bearer <token>`. A kitchen whose own address is `https://localhost` treats that origin as a browser's. Nothing else of the server is open to them, and a loopback server without sign-in answers them like any other site. SECURITY.md and the hosting guide describe the code, the token and what the HTTPS proxy must pass.

### A recipe from a link

**Add › From a link** takes a recipe page's address, and the kitchen reads the recipe the site publishes for search engines (schema.org Recipe JSON-LD: name, yield, ingredients, steps and sections, times, course and cuisine) into a draft to check beside its original, like a paste or a photo. The page's address becomes the recipe's source. A page without that data says so and offers Paste. The new tool `recipe_import_link` does this for MCP agents too; it is the only tool marked open-world, and its description tells agents to call it only for a link the user asked to import.

This is the first time the server fetches anything, so the fetch is guarded (`mcp/fetch-page.js`), with the security thread's notes:

- Only http and https, on the standard ports, without credentials.
- Literal addresses are checked on every hop. Every address a name resolves to must be public, and the connection goes to the address checked. Loopback, `0.0.0.0`, private, shared, link-local and metadata, multicast, reserved and documentation ranges are refused, with their IPv4-mapped, IPv4-compatible, NAT64, 6to4 and Teredo forms.
- Names are resolved by DNS queries that give up after a few seconds rather than the system lookup, which holds one of Node's four pool threads until the name answers.
- At most five redirects, 3 MB after decompression and 10 seconds.
- Its own agents, without keep-alive or proxy, and certificates checked.
- One generic message whatever the site answered, so nothing it says is repeated.
- No images or other resources are fetched, and the page is not kept. Only the recipe's fields are read, as text, from blocks found by scanning rather than one pattern over the page. The scan lowercases ASCII only, so a title with "İ" (which lowercases to two characters) does not shift it.
- At most two pages at once, and 30 an hour from one client address.

SECURITY.md, the hosting guide (outbound access, and the site seeing the server's address), the MCP guide and decisions say so. Docs that still described click-to-play video players, which the redesign replaced with links that open in a new tab, are corrected.

### Ask Kooks, the assistant

A household whose host sets `KOOKS_ANTHROPIC_API_KEY` gets **Ask Kooks**, beside Household in the top bar and at the rail's foot. A member asks about the recipes, the week or the groceries, or taps a starter, and sees what the assistant is doing while it reads ("Looking through your recipes"). The answer is plain text, with a card for each change it suggests: plan a dish on a day, add things to the groceries, shop for a week or a dish, or save a recipe draft. The card describes the change from the kitchen's own records, and nothing changes until the member taps Plan it, Add them, Choose what to buy or Save the draft, through the usual tools, so history and Undo apply. The next question tells the assistant what became of its suggestions. The conversation lasts until Start over or the tab closes. Without a key, Ask isn't shown and its address says how to turn it on.

The server (`web/assistant.js`) calls Claude through the Anthropic SDK with adaptive thinking, medium effort, prompt caching and server-side fallback to another model when the default is overloaded. The assistant has the kitchen's read-only tools, without stored files, import drafts, history or sign-in data, and four proposal tools whose input is checked against the schemas and the records; it has nothing that changes the kitchen or reaches the web. A member asks one question at a time and 30 an hour, the kitchen 300 a day; a question carries at most 60,000 characters of the conversation before it (the app sends the latest turns that fit), makes at most eight model calls, reads at most 120,000 characters and stops after three minutes with a plain message, and a daily token allowance kept in the database (`KOOKS_ASSISTANT_DAILY_TOKENS`, two million by default) stops it once spent. API errors are logged by status only, a refused call names `KOOKS_ASSISTANT_MODEL` in the log, and members get plain messages.
