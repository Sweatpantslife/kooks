# Security policy

## Supported versions

Kooks has no releases yet. Fixes land on `main`, so run the latest commit of `main`.

## Reporting a vulnerability

Report it privately through GitHub: on the repository's **Security** tab choose **Report a vulnerability**, or open [a new advisory](https://github.com/Sweatpantslife/kooks/security/advisories/new) directly. Please do not open a public issue or pull request for a vulnerability that is not fixed yet.

Include what you found, how to reproduce it (steps or a proof of concept), the commit you tested and how that server was set up: loopback only, shared on a private network with a plain-HTTP `KOOKS_PUBLIC_ORIGIN`, or hosted behind HTTPS. Use synthetic data. Never send a real household's cookbook, sign-in links or codes, session cookies, device tokens or passkey material.

The report, the fix and its disclosure are coordinated in the private advisory. The advisory is published once the fix is on `main`.

## What Kooks protects

[Hosting](docs/hosting.md) and [household features](docs/household-features.md) describe the model in full. In short:

- The browser server (`web/`) binds to loopback and asks nobody to sign in. Any other address, a `KOOKS_PUBLIC_ORIGIN`, `KOOKS_OWNER_EMAIL` or a household address list turns sign-in on, and beyond loopback the server only answers to the host in `KOOKS_PUBLIC_ORIGIN`. Only people with an account get in, with a passkey or a one-time emailed link; accounts come from `KOOKS_OWNER_EMAIL` and from invites a member sends (or from any address with `KOOKS_OPEN_SIGNUP`). Each household's cookbook is its own SQLite file, and every request is checked against the session's current membership, so a removed member is out at their next request. Sessions are HttpOnly, SameSite=Strict cookies that slide to 180 days from the last day of use, and members can sign any of their devices out. Behind HTTPS the cookies are also Secure and responses send HSTS. The phone app asks for a link and waits with a 256-bit secret of its own; the link's page signs nobody in until the person there confirms that the app may sign in, and the app then receives a device token, sent in an `Authorization` header. Only the Capacitor origins `capacitor://localhost` and `https://localhost` may call `/api/` across origins, only with sign-in on, and their requests never count a cookie; opening links and invites and passkeys are refused from them whatever they carry. A kitchen whose own address is `https://localhost` treats that origin as a browser's. Each change in a cookbook records who made it by an opaque account id (or as an MCP agent's, or the kitchen computer's when sign-in is off), never by address; a member's link to a person at the table is kept with their membership in the sign-in tables, so a household's cookbook file and its portable backups hold no sign-in addresses, and history names members to each other by the person at the table recorded with each change, which a later link cannot rename. Members link only themselves; an owner can also take back another member's link.
- The MCP server (`mcp/`) speaks stdio to the agent that started it, trusts that agent with the cookbook and tells it to treat recipe and source text as data, never as instructions.
- Recipe links are stored and opened in the member's own browser. The server fetches a web page in one case only: when a member, or an MCP agent the member asked, adds a recipe **From a link** (`recipe_import_link`). Then it fetches that one page, over http or https on the standard ports, from public addresses only. Every address a name resolves to is checked, literal addresses are checked on every redirect, the connection goes to the address checked, and loopback, private, link-local (cloud metadata), shared, multicast, reserved and documentation ranges are refused, with their IPv4-mapped, IPv4-compatible, NAT64, 6to4 and Teredo forms (`mcp/fetch-page.js`). Names are resolved with DNS queries of its own that give up after a few seconds, not the system lookup, so a name that never answers cannot hold the server's thread pool; the hosts file is not used. It follows at most five redirects, reads at most 3 MB after decompression, for at most 10 seconds, with its own agent and no cookies, credentials or proxy, and with certificates checked. Only the page's schema.org Recipe data becomes a draft; nothing else on the page is fetched, the page is not kept, and an error never repeats what the site answered. The site sees the household server's address. Two pages are read at once at most, and 30 an hour from one client address. The MCP tool is marked open-world and tells agents to call it only for a link the user asked to import. Uploaded photos and ebooks are checked by signature and stored, never summarised by the server; only a photo sent for recipe import is read, by local OCR, and is not sent to a model provider.
- The assistant (**Ask Kooks**, `web/assistant.js`) is the only part of Kooks that sends household data to a model provider, and only when the host sets `KOOKS_ANTHROPIC_API_KEY`; without it `/api/assistant` answers 404. The client is built with that key, the Anthropic endpoint, logging off and tracing off, so none of the host's own `ANTHROPIC_*` settings (another key or token, another endpoint, extra headers, a log level that prints requests) reach it. The key is never sent to the app, logged or kept in a backup. A question goes to Anthropic with the conversation so far and what the assistant reads with the kitchen's read-only tools: recipes, meals, plans, groceries, pantry, equipment, notes and sessions, leftovers, prices and budgets, techniques, ideas, books, and members' names, tastes and diet labels. Assets, import drafts, history, backups and sign-in data are never read. The assistant has no tool that changes the kitchen and none that reaches the web. A change it suggests comes back as a proposal, checked against the schemas and records, that the app describes from its own fields and records rather than the assistant's words, and makes only when a member taps it, through the usual tools with a request id of its own, so history and Undo apply. Replies are shown as plain text: nothing the assistant writes becomes a link, an image or markup. Record text is described to the model as data, since a link import brings any website's text into the kitchen; what it can do with an instruction hidden there is limited to what it says and what it suggests. A member asks one question at a time, 30 an hour, and the kitchen 300 a day; a question carries at most 60,000 characters of conversation, makes at most eight model calls, reads at most 120,000 characters and lasts at most three minutes, and a daily token allowance kept in the database stops it once spent. Errors from the API are logged by status only and reach members as plain messages.
- The phone app is the browser app packaged with Capacitor. It keeps the kitchen's address, its device token, a read-only copy of the kitchen and grocery ticks waiting to be sent in its web storage, which Android's backup rules leave out and sign-out clears, and its page carries its own content security policy (`client/page-policy.js`) that lets it reach only https addresses besides itself. The recipes the previous phone app kept in its private storage are read once and sent to the kitchen only when the member asks.
- The automatic backups (`web/backups.js`) are whole copies of the server's databases, so they hold every household's records and files and the sign-in tables: account addresses, passkeys' public keys and the hashes of session and device tokens, never a token itself. They are written readable by the server's user only, in a folder of their own beside the database, and leave the server only when its operator copies them off. Only the address in `KOOKS_OWNER_EMAIL` sees their details in the app; `/healthz/backups` tells anyone only when the last copy was taken. A restore is staged from the server's own terminal and takes effect at the next start.
- Off-site copies (`web/offsite.js`) send those same whole copies to the bucket in `KOOKS_BACKUP_S3_URL`, over HTTPS only, signed with AWS Signature Version 4 and checked by the storage against each file's SHA-256. The key lives only in the deployment's secrets; the log, the owner's Backup page and the error messages name the bucket's host and folder, never the key. The server only writes there, so the recommended key can't read, list or delete, and a broken-into server can't take the older copies with it; the bucket's lifecycle rule does the pruning. Kooks does not encrypt the copies itself, so the bucket must be private, and the provider's encryption at rest is what protects them there.
- `scripts/accounts.mjs` is for whoever runs the server, from its terminal: it lists accounts and households, prints a one-time sign-in link for an address that has an account, makes an address an owner of a household, and deletes an account. Someone at that terminal can already read and change the database, so it gives them nothing new; it spares them editing tables by hand when the owner's mailbox is gone. The link is printed, never emailed or logged, and is the same 15-minute, single-use link as an emailed one. No route reaches the roster, the owner change or the deletion (`roster`, `grantOwner` and `deleteAccount` in `web/auth.js`), and the owner change signs nobody in. A member removed under Household › Members keeps an account, which can still sign in and start a household of its own; when someone else may hold an old address's mailbox, `remove` deletes the account with its passkeys, sessions, waiting links and invitations, and leaves the address nowhere in the sign-in tables. It keeps a household's last owner, and the `KOOKS_OWNER_EMAIL` address, which the server would give a new account at its next start; a household the address alone is in stops it unless `--leave-empty` says to leave that household with nobody in it, where only `owner --household` can put someone back.

Reports about any of these are in scope, as are the dependencies Kooks ships. Out of scope: attacks that need control of the machine or account running Kooks, of the MCP host agent or of the deployment's environment variables, and the documented limit that plain-HTTP LAN sharing is unencrypted.

## Dependencies

Dependabot security updates are enabled, and `npm audit` should report no vulnerabilities on `main`.
