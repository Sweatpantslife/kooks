## Setup and entry points

Use Node.js 22.13 or newer. Install from the committed lockfile with `npm ci`.

| Command                 | Purpose                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `npm run dev`           | Browser/SQLite server at `http://127.0.0.1:4317` (run `npm run build:client` first)     |
| `node mcp/index.js`     | MCP stdio entry point; use an absolute executable/script path in a client               |
| `npm run build:client`  | Builds the browser app into `client/dist`, which the server shows at `/`                |
| `npm run dev:client`    | The browser app with live reload at `http://127.0.0.1:5174`, using the server on 4317   |
| `npm run test:coverage` | Unit tests with a coverage table; also writes `coverage/lcov.info` for CI's job summary |
| `npm run test:e2e`      | The Playwright suite                                                                    |
| `npm run format:check`  | Prettier check enforced by CI; `npm run format` rewrites files                          |
| `npm run lint`          | ESLint's recommended rules, enforced by CI (`eslint.config.js`)                         |
| `npm run cap:sync`      | Build the client and copy it and the plugin configuration into both native projects     |
| `npm run native:doctor` | Diagnose required native tooling                                                        |
| `npm run build:ios`     | Unsigned simulator app; not a physical-device IPA                                       |
| `npm run build:android` | Debug APK; not a signed store release                                                   |

Private cookbook data defaults to `.data/kooks.sqlite`. Tests use temporary or in-memory databases; use `KOOKS_DB_PATH` to isolate manual testing too. Do not seed tests from a personal cookbook. Generated assets and dependencies are excluded from Git and recreated by installation/build/sync.

Backend schemas live in `mcp/schemas.js`, `mcp/feature-schemas.js` and `mcp/library-schemas.js`; keep validation and write behavior shared across browser and agent tools. Preserve optimistic versions, request IDs, snapshot semantics, and shopping preview tokens when adding new clients.

Native setup expected by the checked-in project: Xcode 26+ with iOS SDK/simulator on macOS; JDK 21+ and Android SDK Platform 36/build tools for Android. iOS deployment target is 15; Android minimum API is 24. `scripts/native-build.mjs` checks tooling. The publication environment still lacks the required native setup. Device signing and store credentials must remain outside Git.

## Meaningful verification

```sh
npm run format:check
npm run lint
npm test
KOOKS_TEST_OCR=1 npm test
npm run test:e2e
npm run cap:sync
npm run native:doctor
```

`npm test` covers domain rules, backup round-trips, independent SQLite connections, real MCP client persistence, HTTP sign-in (emailed links, passkeys from a software authenticator, sliding sessions, revocation and throttling; the phone app's emailed codes, device tokens and cross-origin rules), and the phone app's notification reconciliation, kitchen addresses and import of the previous phone app's recipes. `test/webauthn.test.js` covers passkey verification for ES256, RS256 and Ed25519; `test/mail.test.js` covers the SMTP client against a fake server with STARTTLS and implicit TLS (when `openssl` can mint a certificate) and the file outbox. The OCR case is skipped unless explicitly enabled. macOS OCR needs command-line tools and system image services; other platforms need Tesseract. HTTP tests require permission to bind loopback ports. `test/assets.test.js` covers schema 2 image storage and its in-place upgrade; `test/library.test.js` covers file checks, techniques, ideas, the shelf and their backups; `test/backup.test.js` covers the streamed backup download, file restores at any read size and the files they refuse; `test/shared.test.js` covers the shared tokenizer and the shared link module; `test/ocr-cache.test.js` covers the compiled-helper cache without clang.

Playwright uses its managed Chromium by default (`npx playwright install chromium` once); `PLAYWRIGHT_CHANNEL=chrome` uses an installed Chrome and `PLAYWRIGHT_EXECUTABLE_PATH` points at a specific binary. The web project builds the browser app and starts `web/server.js` twice on fresh temporary databases: on port 4318 without sign-in, and at `http://localhost:4319` with sign-in on (`KOOKS_HOUSEHOLD_EMAILS` and a file outbox). It covers the tabs and Household, pasted and photographed drafts, writing and editing recipes with unsaved-change guards, the cookbook's search, kinds and filters, What can I make?, meals, the week and its plans, groceries by aisle through to At home, cooking with timers, notes and leftovers, people and tastes, prices and the weekly budget, units, backup, ideas, techniques and the book shelf, the previous app's addresses, other cooks' changes arriving while someone types, Undo and its focus, every page at 320, 390, 768 and 1280 px, sign-in by emailed link and passkey through Chromium's virtual authenticator, and the phone's sign-in with a kitchen address and an emailed code, in a browser. No test executes native plugins. axe-core (`@axe-core/playwright`, through `test/axe-scan.js`) runs against WCAG 2.2 A and AA plus axe's best practices, in the light and dark themes: in the web project on every tab and Household at phone and desktop widths and on each page the tests visit, including both sign-ins. Any violation fails the test with the page, theme, rule and elements. Use synthetic records.

Dated results for each change, with the checks run, their counts and what was not exercised, are in the [changelog](../CHANGELOG.md).

## Ordered continuation work

1. **Establish a reproducible native baseline.** Install the tooling, run doctor/sync and both native builds, then test on actual iOS and Android devices. Acceptance: record versions/results for cold launch, keyboard/safe areas, back navigation, sign-in against a real kitchen, sharing a book and a backup, termination/relaunch, notification permissions, a timer cancelled on another device, and locked-screen delivery, and bringing in recipes from the previous phone app. Document platform timing limits; Android ordinary notifications do not guarantee exact alarms.
2. **Widen what the phone does without a connection.** The phone shows its copy of the kitchen and keeps grocery ticks until the kitchen answers. Decide which other changes are worth keeping offline (cooking progress, adding a grocery, a cooking note) and how each meets changes made meanwhile, reusing request IDs and optimistic versions so retries never duplicate and stale edits are refused rather than lost. Acceptance: each such change made offline arrives once; a conflicting change is shown, not overwritten; photos are available offline if that is wanted.
3. **Finish household identity.** Sign-in exists in `web/auth.js`: passkeys plus one-time emailed links against the configured address list, sliding sessions, sign-out, and revocation by editing the list. Remaining: an invitation flow inside the app instead of an environment variable, linking member profiles to sign-in identities, per-household authorization if several households share a server, and signing out other devices. Acceptance: an invited member signs in with no operator involvement; an unrelated household cannot read or mutate records; a removed member's sessions and passkeys stop at once; link expiry, passkey removal and network failures are covered in the browser.
4. **Exercise the household additions on phones.** The phone app is the same client, so the eight additions are there. Acceptance: each workflow is exercised on both platforms with synthetic records, including rejected over-allocation, stale shared tasks, incomplete costs, unknown effort/spice, preferred variants, and required image review.
5. **Implement supported AI connections and live assistance.** Recheck provider documentation, choose approved login or explicit API-key fallback and billing, and define autonomy/data-sharing boundaries. Start from the MCP action contracts. Acceptance: actual login/cancel/expiry/reconnect/revocation for each selected provider; a real recipe or meal request produces a reviewable validated action; undo, retries, stale data, provider failure, and manual continuity work. Never embed provider secrets in client bundles or claim consumer login equals API entitlement.
6. **Complete the pilot and release process.** Validate languages/units, accessibility, realistic import samples, and cooking behavior with an agreed pilot. Settle incoming sharing/URL import and advanced scheduling requirements explicitly. Acceptance: platform builds and all relevant checks pass; release scope and known limitations are documented; signing/distribution, hosted service configuration if selected, backup/restore recovery, and support/update procedures are ready. Source publication alone does not satisfy this gate.

These are ordered implementation steps, not claims that one person must finish every item before independent work can proceed. Do not implement speculative features simply because older documents mention them.

## Documentation precedence and publication privacy

Use this handoff, `docs/decisions.md`, `docs/ia-ux.md` for navigation and interface structure, and current implementation guides as status authority. Research, product brief, project plan, meal design, and prototype review retain historical rationale but carry a superseded-status notice. In particular: platform choice is settled; browser/MCP batching, photos, history, and backups now exist; native compilation and connected AI remain unfinished.

The public snapshot excludes runtime databases/WAL files, personal uploads/photos, cookbook backups, environment files, signing credentials, logs, local tooling, and generated outputs. Personal discovery context was removed from public documentation; original notes remain local in the ignored data directory. Bundled recipes and the OCR image are synthetic examples, not a household archive. Review the exact staged content and full included Git history for every future public push; ignore rules cannot protect already-tracked private files.
