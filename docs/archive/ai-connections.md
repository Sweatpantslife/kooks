## Proposed experience

The Assistant area contains AI connections for OpenAI/ChatGPT and Claude. A connection reports its actual state: not connected, connecting, connected, expired, unavailable, or disconnected. Provider choice belongs to the user; a failure must not silently switch providers or send recipe content to another service.

Begin account sign-in inside Kooks, open the provider's official authorization flow, and return to the app when the supported integration reports success. Kooks must not collect provider passwords or claim a connection merely because a login page was opened. Show the actual account and connection type after verification; do not display invented remaining-credit values.

If API-key fallback is accepted, distinguish it from account sign-in in the interface. Explain the applicable usage billing, validate a connection without exposing the key, allow revocation, and keep secrets out of source control, browser storage, analytics, logs, recipe exports, and the prototype. Decide whether credentials are personal or belong to an expressly configured household service account; household membership should not grant access to another person's key or subscription.

Provider connections are separate from signing into the Kooks household. Both providers call the same narrowly scoped recipe, meal, list, and cooking actions. A runtime integration must not give the cooking assistant general access to the user's computer merely because the underlying agent supports it.

A local MCP companion is also present in this workspace (`mcp/server.js`, `mcp/tools.js`). Source inspection shows cooking actions exposed to a host agent, with no built-in model-provider connection. It is a candidate action interface for integration, not evidence of completed in-app account sign-in. Its implementation is separate from the experience prototype and was not changed or tested in this review.

## Phase 1 feasibility gate

1. Confirm whether existing subscription access is mandatory or API-key fallback is acceptable. No fallback is assumed.
2. Inspect the supported OpenAI runtime route, login callback/device flow, session isolation, permitted deployment, and phone-to-service architecture. Keep experimental transports out of a production commitment.
3. Resolve a supported Claude account route/approval or agree on the API alternative. Reconcile documentation with actual provider support before promising subscription-funded use.
4. Present a concrete choice: what runs on the phone, what requires a service or companion, which account pays, and what happens when that service is offline. Do not commit the stack before this affects the platform choice.
5. When implementation begins, verify login, cancellation, expiration, reconnection, revocation, and a narrowly scoped sample action on each approved provider. A proof for one provider does not validate the other.

The current preview demonstrates meal actions with sample data. It intentionally has no active sign-in or credential entry. Autonomy and multi-day batch cooking are separate pending product questions.
